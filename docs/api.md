# Standalone alpha HTTP API

All application routes are below `/garage-api`. `GET /garage-api/capabilities` advertises `backend: standalone`, `apiVersion: 1` and supported feature names, including `measurementCorrections`. These endpoints belong to Wolfs Garage; they are not LubeLogger endpoints.

The configured public host/port must match requests. Every write requires JSON, `Origin` equal to `GARAGE_PUBLIC_ORIGIN` and `X-Garage-Request: 1`. If supplied, `Sec-Fetch-Site` must be `same-origin`. These checks are not authentication. The deployment must protect non-local access through its authenticated proxy.

| Method and path | Payload / result |
| --- | --- |
| `GET /vehicles` | `{vehicles: [...]}`; each vehicle includes stored mileage settings and derived `mileageEstimate` and `readingPrompt` projections. |
| `POST /vehicles` | `make`, `model`; optional `year`, `licensePlate`, `vehicleType`, `odometerUnit` (`km`, `mi`, `h`), `name`, `inspectionDueMonth` (`null` or `YYYY-MM`, years 0001–9998), `annualUsage` (null or decimal string 0–1,000,000,000 with up to three fractional digits), `readingPromptDays` (null or integer 1–3650; defaults to 30). Returns vehicle with derived inspection/readiness and mileage/prompt projections. |
| `GET /vehicles/{id}` | Vehicle including revision, current reading, raw manual status, derived inspection/effective-readiness projection, stored mileage settings, and derived mileage/prompt projections. |
| `PUT /vehicles/{id}` | Expected `revision` plus fields to change; unspecified fields are preserved. `inspectionDueMonth` and `annualUsage` can be explicitly cleared with `null`; `readingPromptDays: null` disables the prompt. Changing the unit when readings exist is forbidden; without readings, changing unit while a rate is set requires explicitly clearing or setting `annualUsage`. Returns vehicle. |
| `GET /vehicles/{id}/summary` | `{vehicle, status, reminders: [], services: [...]}`. `vehicle` includes the same mileage settings and projections as the vehicle route. This alpha has no recurring maintenance reminder engine. |
| `GET`, `PUT /vehicles/{id}/status` | `{readiness, issues: [{id, text, dueDate, severity, lifecycle}], revision}`. `dueDate` and `severity` may be `null`; severity is `observation`, `repair`, or `critical`; lifecycle is `open` or `observed`. Legacy `{id,text}` rows are normalized on read. New issue IDs are generated; existing IDs must belong to this vehicle. |
| `GET /work` | Read-only `{today, timeZone, items:[{vehicleId,id,text,dueDate,severity,lifecycle,dueState}]}` projection of active open/observed work across vehicles. This route accepts no query parameters. |
| `GET /export` | Download the portable owner-data JSON export as `wolfs-garage-export.json`; no query parameters. Advertised as `dataExport`. |
| `GET /backup` | Download a consistent full SQLite snapshot as `wolfs-garage-backup.sqlite3`; no query parameters. Advertised as `databaseBackup`. |
| `GET /vehicles/{id}/odometer` | `{readings: [...]}` with dated history. |
| `GET /vehicles/{id}/odometer/page` | Bounded `{readings: [...], nextCursor: null|string}` history page; optional `from`, `to`, `limit`, and opaque `cursor`. |
| `POST /vehicles/{id}/odometer` | `date`, `odometer`, `unit`, `commandId`; optional `note`. Returns a reading with `revision=1`, `provenance=manual`, and null `sourceRecordId`. |
| `GET /vehicles/{id}/odometer/{readingId}` | `{reading}` with exact decimal text, revision, provenance and optional source record ID. |
| `PUT /vehicles/{id}/odometer/{readingId}` | Manual-reading correction only: `revision`, `date`, exact decimal-string `odometer`, `note`, `commandId`, `correctionReason`. Returns the corrected reading and current-reading projections before/after. |
| `PUT /vehicles/{id}/odometer/{readingId}/provenance` | Explicitly classify only an unresolved legacy reading as `manual` or `record`. Record linking requires `sourceRecordId` and `recordRevision`; manual classification requires both to be null. A reason and reading revision are required. |
| `GET /vehicles/{id}/records` | `{records: [...]}` |
| `GET /vehicles/{id}/records/page` | Bounded `{records: [...], nextCursor: null|string}` page; optional `from`, `to`, `limit`, `cursor`, and `kind` (`service` or `repair`). Rows keep the existing full record shape. |
| `POST /vehicles/{id}/records` | `description`, `kind` (`service` or `repair`), `date`, `commandId`; optional reading, cost/currency, document reference and selected issue closure. If the record includes an odometer, its reading is created and linked atomically. Returns `{record, status}`. |
| `GET /vehicles/{id}/records/{recordId}` | One record including its current `revision`; the record must belong to the requested vehicle. |
| `GET /vehicles/{id}/records/{recordId}/measurement` | `{record, odometerExact, sourceReading, correctionMode, currentReading}`; mode is `linked`, `date_only` or `legacy_unresolved`. |
| `PUT /vehicles/{id}/records/{recordId}/measurement` | Requires `revision`, `readingRevision` (or null for date-only), `date`, `odometer` (exact decimal string, or null for date-only), `commandId`, and `correctionReason`. Returns `{record, reading, currentReadingBefore, currentReadingAfter}`. |
| `PUT /vehicles/{id}/records/{recordId}` | Full replacement of editable fields using exactly `revision`, `commandId`, `description`, `kind`, `cost`, `currency`, `documentUrl`, `correctionReason`. Returns `{record}` and increments `revision`. |
| `GET /vehicles/{id}/history` | `{events: [{sequence, action, occurredAt, before, after}]}` |

Dates are ISO calendar dates (`YYYY-MM-DD`); history timestamps are UTC. Cost is an exact decimal **string**, nonnegative with at most two fractional digits, and requires an explicit uppercase three-letter currency. No conversion is performed. Reading `odometer` remains numeric for compatibility; `odometerExact` carries the stored decimal string. Current reading follows the latest date and then descending reading ID; it is not the maximum value. A vehicle's unit cannot be relabelled after readings exist.

Paged history is advertised by the `historyBrowsing` capability. `from` and `to` are optional inclusive ISO calendar dates. `limit` defaults to 25 and must be 1–100. `kind` is supported only for records. Unknown, duplicate, empty, or invalid query parameters return `400`. Rows sort by date descending and stable ID descending. The continuation cursor is opaque and binds the vehicle, resource, filters, limit, last sort key, and latest vehicle audit sequence. Wrong-context or malformed cursors return `400`; a vehicle change since the page was issued returns `409` and requires restarting at the first page. Each page reads its rows and audit sequence in one SQLite read transaction. These routes do not modify history or schema. The legacy unpaged `GET /vehicles/{id}/records` and `/odometer` responses are unchanged. Full details and browser acceptance behavior are in [history browsing](planning/history-browsing.md).

Scheduled work is advertised by `scheduledWork`. Status updates may set an optional ISO date, nullable severity (`observation`, `repair`, `critical`) and lifecycle (`open`, `observed`) for each issue. An omitted field on an existing issue preserves its value; explicitly sending `null` clears `dueDate` or `severity`. Lifecycle cannot be `null`; completion removes the selected issue through the existing atomic record workflow. Read responses always include all issue fields; old stored `{id,text}` rows read as null due date/severity and lifecycle `open`. Severity is user supplied and may remain null; no classification is inferred. `GET /work` accepts no query parameters. The app evaluates the current Berlin calendar date once per read transaction and derives `overdue`, `today`, `upcoming`, or `unscheduled`; critical items sort first, followed by due state, due date ascending, vehicle ID, then issue ID. Projection reads do not add audit events or mutate status. Contract and acceptance details: [scheduled work](planning/scheduled-work.md).

Portable owner-data export is advertised as `dataExport`. `GET /export` returns a JSON attachment and accepts no query parameters; a query string is a `400`. It contains format version 4, application/schema version, export timestamp, stored vehicles/statuses, odometer readings, completed records and decoded application history, ordered by primary key. Reading rows include exact decimal text, revision, provenance and source record ID; legacy audit JSON keeps its original recorded types. Stored vehicle metadata includes raw `inspectionDueMonth`, `annualUsage` and `readingPromptDays`; derived `inspection`, `effectiveReadiness`, `mileageEstimate` and `readingPrompt` are omitted. The endpoint uses the configured host boundary, returns `Cache-Control: no-store`, and does not modify the database. It excludes command replay state, configuration/secrets, dashboard projections and external document bytes; it is not an import format or a restorable database backup. See [owner data export](data-export.md).

Full database backups are advertised as `databaseBackup`. `GET /backup` accepts no query string and returns a checked SQLite snapshot attachment named `wolfs-garage-backup.sqlite3`, with `Cache-Control: no-store`. The snapshot includes the complete database, including command replay state; it preserves the source schema and does not migrate it. A private temporary snapshot is removed when the response closes, including on backup failure. The endpoint uses the configured host boundary; it is a sensitive administrative download and must only be reachable behind the authenticated access boundary. For restoration, the CLI validates integrity, foreign keys and supported schema 1–6, then copies into a new exclusive destination. It never replaces the configured live database, overwrites an existing file, or migrates a schema. See [backup and update workflow](planning/backup-update-workflow.md).

The `inspectionStatus` capability adds a read-only calendar projection to public vehicle and summary responses. Its `inspection` object includes `asOf`, `timeZone`, `dueMonth`, `validUntil`, `blockingFrom`, `state`, `monthsUntilDue`, `blocksReadiness`, `batteryLevel`, and `scaleMonths`. A missing month remains `unknown`; it does not produce an inferred deadline. The configured month follows the owner's policy: the due month is `due`, the next month is `overdue`, and blocking begins on the first day two calendar months after the due month. This is not a statement of legal deadlines. `status.readiness` remains the manually stored assessment; `effectiveReadiness` is `not_ready` when that manual state is `not_ready` or inspection state is `blocking`. Updating the month does not change status, issues, or odometer readings. See the [inspection status contract](planning/inspection-status.md).

A record may contain `documentUrl` (HTTPS, no URL credentials); this is only a reference and is never fetched. To close an issue, supply its `closeIssueId` and expected `statusRevision`. The record, optional reading, issue closure and history commit atomically. This never changes readiness automatically.

The `measurementCorrections` capability advertises the separate date/odometer correction routes. Schema 5 introduced reading revision and provenance (`legacy_unknown`, `manual` or `record`) plus an optional source record link; schema 6 adds mileage settings. New work records with an odometer atomically create a linked reading. Existing readings migrate as `legacy_unknown`; notes, equal dates or values never create inferred links. A record with a linked reading can update both dates and exact values atomically using both expected revisions, a reason and `commandId`. A record without an odometer can update its date only. An unresolved legacy record with an odometer remains locked until its old reading is explicitly classified by the owner. Manual readings have a separate correction route; record-linked readings cannot be edited independently. The legacy provenance route changes association metadata only, after the owner selects a record with matching vehicle/date/value/unit and confirms a reason. Values accept at most three fractional digits, including zero. A stale revision or conflicting association returns `409`; validation and audit failures roll back all changes. Successful operations append before/after history and are idempotent by command ID. Responses include current-reading projection before/after because changing date/value may change the latest-date-then-ID projection. Units, vehicle, cost, kind, issue closure and readiness are outside these correction operations. See [measurement corrections](planning/measurement-corrections.md).

The `mileageForecast` capability adds read-only projections to vehicle, summary and list responses. `mileageEstimate` has `{asOf,timeZone,state,annualUsage,unit,anchor:{id,date,odometer,unit}|null,elapsedDays,estimatedOdometer}`; `readingPrompt` has `{asOf,timeZone,state,intervalDays,dueDate,reason}`. `annualUsage` is an optional exact decimal string; `readingPromptDays` is a nullable interval (new vehicles default to 30 days). The estimate uses the latest actual reading by descending date and ID, and projects annual usage over elapsed calendar days using a fixed 365-day denominator. No projection is stored or inserted as a reading. A future anchor, unit mismatch, or result beyond the supported reading range returns a named non-estimated state. The prompt is due on anchor date plus its configured day interval; missing readings prompt the owner to capture an actual reading, and invalid anchors prompt review. A null interval disables the prompt. See [mileage estimate and reading prompt](planning/mileage-forecast.md).

The older bounded record-correction route still applies only to description, service/repair kind, cost, currency and the HTTPS reference. Its strict full-replacement body requires `revision`, `commandId`, `description`, `kind`, `cost`, `currency`, `documentUrl`, and `correctionReason`. It continues not to modify measurement facts, issue state or readiness.

An identical retry with the same `commandId` returns the original response, including after the record revision has advanced. Reusing that command ID with changed content conflicts. A different command against a stale revision returns `409`; a record missing from or belonging to another vehicle returns `404`. These routes use the same configured host, JSON, `Origin`, and request-header boundary as other writes.

Reading/record commands require a UUID `commandId`. Repeating the same vehicle/action/key/payload returns the original result without another write; a changed payload under that key conflicts. Revisions protect metadata/status from stale writes. Vehicle creation does not yet have this retry guarantee: after a lost response inspect the list before retrying.

Errors use `{error: ...}`: invalid values `400`, failed write boundary `403`, absent object `404`, stale/conflicting command `409`, excessive request body `413`, unsupported media type `415`, unavailable database `503`. `/healthz` exposes only storage availability. Fresh databases use schema 6; schemas 1–5 require the explicit checked-backup upgrade command. The CLI supports `export NEW_PATH` for a new `0600` JSON file and `restore-backup SOURCE NEW_DB_PATH` for a validated copy into a new `0600` SQLite file; restore refuses existing paths, symlinks, the source path and configured live database, and does not upgrade. There are no delete operations or file uploads in this alpha.
